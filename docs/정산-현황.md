# 정산 현황 및 확정 규약

최종 갱신: 2026-09-04 · 계산식 개정 소급 적용(036·037·038 + 총액 정정 62건) 완료 기준

세션마다 같은 조사를 반복하지 않기 위한 문서. **금액이 걸린 판단은 여기부터 확인한다.**

- **금액이 셋이다** — 실제 청구액 / 담당자 확정금액 / 시스템 계산값. 셋의 뜻과 비교 규칙은 README 「금액이 셋이다」
- 지금 「확정 − 계산」이 전 차수에서 양수인 것은 오류가 아니라 **소급 미반영분**이다 (2번)

## 1. 확정된 계산 규약 (담당자 확인 완료)

### 중간정산 — 2026-09-04 개정 (담당자 요청, **전 차수 소급**)

```
공급가 = 수입금액USD × (1 + 마진%) × 통관환율
       + 해상운임 + 통관비 (전부 VAT 별도 공급가)
       − 수입부가세           ← 세관 납부분, 매입세액공제 대상
       − 관세                 ← 부가세를 매기지 않는다
부가세 = 절사된 공급가 × 10%
합계   = 공급가 + 부가세 + 관세
```

**모든 비용 항목은 VAT 별도 공급가로 넣는다.** 항목에 붙은 부가세(트럭운송비·대기료 등 국내
발생분)는 **공급가에 더하지 않는다** — 에이원이 매입세액으로 공제받을 몫이라 다시 청구하면 이중이다.
관세는 공급가 밖으로 뺐다가 부가세를 매긴 뒤 합계에 그대로 얹는다.

- 관세는 **이름이 아니라 `interim_cost_items.is_duty` 플래그**로 가른다 (`036`).
  「관세」로 시작하는 행 40개 중 금액이 있는 건 3개뿐이다 (1·34·43차, 합 6,287,060원)
- 구방식(`vat_mode = 'inclusive'`)은 손대지 않는다 — 부가세를 분리할 수 없어 관세만 빼면
  합계가 어긋난다. 2·6·7차가 여기 해당하며 담당자 재입력 대상이다

**개정 전 규약** (2026-09-04 이전, 기록용): `공급가 = … + 항목 부가세 − 수입부가세`,
`합계 = 공급가 + 부가세`. 항목 부가세를 토에이 실지급액으로 보아 매입원가에 넣었다.

- 단 `inclusive` 모드는 `itemVat`을 더하지 않으므로 이 부가세가 통째로 사라진다 (2차 +58,400의 원인)

### 최종정산(클로징)

```
환차손익 = 원금 × 통관환율 − LC 결제비용        (양수 = 환차익)
공급가   = ((LC 부대비용 − 환차손익) + 기타 미정산 비용(A+B+C)) × A1 부담비율
부가세   = 절사된 공급가 × 10%
합계     = 공급가 + 부가세
```

- **부호**: 지불 양수 / 환급 음수
- **A1 부담비율**: 34차까지 50%, 35차부터 100%. 35차 이후 클로징이 아직 없어 소급 대상 없음
- **기타 미정산 비용(A+B+C)에도 부담비율을 곱한다.** 원본 문서가 이 항목만 부담비율 밖 전액으로 둔 것이 오류였다
  - `lib/calculations/closing.ts`의 `a1ClosingCostsKrw`. 신·구방식 모두 적용
  - `closingCostsTotalKrw`(원금)는 항목 목록 표시용, 공급가에는 부담분만 들어간다
  - A+B+C ≠ 0 인 차수는 **1·2차뿐** (라이브 DB 전수 확인)

### LC 결제비용 — 선지급금 별도 환율

```
LC결제비용 = round(선지급$ × 선지급환율) + round(잔액$ × 클로징환율)
```

구간별로 반올림해 더한다. 은행이 구간별로 결제해 청구하므로 합계를 한 번에 환산하면 원 단위로 어긋난다.
선지급금이 0·NULL이면 기존과 동일(총액 × 클로징환율)이라 기존 정산 계산은 변하지 않는다.

### 절사

- 0 방향 버림 = 절대값 기준. 음수(환급)도 동일
- 절사는 **공급가**에 건다. 합계에 걸면 공급가 + 부가세 ≠ 합계가 되어 세금계산서가 안 맞는다
- 적용 시작: 중간정산 17차부터 / 최종정산 29차부터
- **소급하지 않는다.** 과거 차수는 저장된 정책 스냅샷 그대로 둔다
  - 소급 시 변동폭 −98 ~ +99원인데, 지금 문서와 정확히 맞는 차수(3·5·9·19차 등)가 오히려 틀어지고 이미 발행된 세금계산서와 어긋난다
  - 29~34차는 전부 `floor_100` 으로 정리 완료

## 2. 확정금액 재입력 — 37개 차수 (2026-09-04 소급 이후)

**「확정금액 − 계산값」이 지금 전 차수에서 양수인 것은 오류가 아니다.** 09-04 계산식 개정을

### 담당자 수기검산 대조 (2026-09-05, 라이브 DB)

담당자가 보낸 숫자를 그대로 재현해 봤다. **청구·지급은 완전히 일치한다.**

| 기준 (1~35차, 2·3차 제외) | 금액 |
|---|---|
| 청구 누계 | 3,156,778,502 |
| 지급 누계 | 3,157,463,987 |
| **청구 − 지급** | **−685,485 (더 지급)** ← 담당자 「약 68만 더 지급」과 일치 |

**계산 기준은 아직 안 맞는다.** 담당자는 「300 정도 덜 지급」이라 했는데 우리 값은 이렇게 갈린다.

| 기준 | 계산 − 지급 |
|---|---|
| 1~35차 (2·3차 제외) | 17,083,922 더 지급 |
| ↑ 6·7차(구방식) 제외 | 5,779,513 덜 지급 |
| ↑ 35차(오기입 건) 제외 | 295,738 덜 지급 |

「300」이 **30만**이면 마지막 줄과 맞고, **300만**이면 담당자 기준에 우리와 다른 지점이
하나 더 있다. **확인 필요.**

#### 35차 청구 오차는 담당자 지목대로 전액 설명된다

담당자 메모 예시(「오기입 2건 — 통관환율 실 1479.34 / 입력 1439.26, 배송비 실 약 177만 /
입력 약 17만」)를 검증했다. **DB 는 이미 정정된 값을 들고 있다** (환율 1479.34,
운송비 항목 합계 1,745,085). 두 오기입의 영향을 되짚으면

```
(80,497.5 × 1.05 × 40.08) + (1,745,085 − 170,000) = 4,962,742
4,962,742 × 1.1 = 5,459,016
```

화면의 35차 「청구−계산」은 **−5,483,717**. 차이 24,701원(절사·배송비 어림값)뿐이라
**청구서가 틀린 것이 맞다.** 확정금액이 계산값과 일치하므로 계산 문제가 아니다.

### 구방식(`inclusive`) 잔존 3건 — 2·6·7차뿐이다

라이브 DB 중간정산 41건 중 이 셋만 `inclusive` 다. 원본 CSV 마지막 열이
「+ 부가세 제외(7%)」= 공급가인데 그 값이 그대로 확정금액이 되어 **매출부가세 10%가 빠졌다.**

신규약은 구방식을 손대지 않는다 — 부가세를 분리할 수 없어 관세만 빼면 합계가 어긋난다.
**재입력하면 자동으로 `exclusive` 로 넘어가고 확정금액이 크게 뛴다**(각 +1,100만~1,200만).
이미 발행된 세금계산서와의 정합을 먼저 확인할 것. 담당자 재입력 대상(1~10차)에 포함돼 있다.

6·7차 수입부가세(6차 10,530,210 / 7차 10,751,980)는 아직 적재하지 않았다 —
`exclusive` 전환과 **반드시 같이** 넣어야 한다. 구방식은 비용을 빼지 않고 전부 더하므로
지금 넣으면 그대로 공급가에 얹힌다.

### 23차 클로징 — 아직 그대로다 (확정 −59,350,700)

### 37차 — 수입금액 기준과 과세환율 2건

**신고가 2건이고 과세환율이 서로 다르다** (2026-09-02 유니패스 확인).

| B/L | 컨테이너 | 카톤 | 수입신고번호 | 신고일 | 고시환율 |
|---|---|---|---|---|---|
| KULFE2600**429** | NSSU7161942 | 3,760 | 02012014260180893A | 2026-05-29 | **1504.04** |
| KULFE2600**428** | NSSU0215292 | 1,380 | 02012014260180889A | 2026-06-01 | **1507.15** |

DB `customs_exchange_rate` 는 1504.04 하나뿐이다 — **429 기준**이고 428분에는 1507.15가 적용됐어야 한다.
카톤 비율(1,380/5,140 = 26.85%)로 추정한 영향은 **약 11.5만원**이나, 카톤 수와 금액 비율이
같다는 보장이 없어 **추정치**다. 신고필증 428·429의 과세가격을 봐야 확정된다.

구조적으로 `transactions.customs_exchange_rate` 가 차수당 1개라 **한 차수에 신고 2건이고
환율이 갈리면 표현할 방법이 없다.** 서류 확인 후 스키마를 손댈지 판단한다.

수입금액도 DB 119,412$(수기금액) vs 통관금액 119,452$ 로 **40$ 차이**(≈63,170원)가 남아 있다.

### 1·2차 클로징 — 부담비율 재입력

부담비율 50% 적용: 1차 기타 미정산 44,000 → 22,000 / 2차 333,400 → 166,700.
현재 클로징 확정은 1차 −180,400 / 2차 6,669,400.

**단, 이 항목들을 클로징에 두는 것 자체가 재검토 대상이다.** 담당자는 중간정산으로 옮기자고
제안했다 — 1차 운송추가운임 44,000(디머리지·대기료), 2차 통관보수료 182,600 + 검역수수료 110,000
+ 운송추가운임 40,800 = 333,400. 성격상 통관·운송 실비가 맞다.
**옮기면 에이원 부담이 50% → 100%가 된다**(1차 +22,000 / 2차 +166,700, 부가세 별도).
A+B+C ≠ 0 인 차수는 1·2차뿐이라 영향 범위도 이 둘로 끝난다.

1차는 **선지급금 백필**도 함께 넣는다. 저장된 LC결제비용 72,782,080원은 클로징환율 1202.4로는
나오지 않고, 선지급금 7,040$에 1156.4를 적용하면 원 단위까지 맞는다. 금액 변동 없음:

```sql
UPDATE closing_settlements
   SET lc_payment_total_usd = 60800, advance_payment_usd = 7040, advance_exchange_rate = 1156.4
 WHERE id = '0afc9658-046c-413b-b66e-1d195af87550';
```

## 3. 원본 문서의 좌측 「LC 이자비용」 열 — 은행서류 차수 순으로 적혀 있다

**원본을 복사하다 밀린 것이 아니다.** `_source_docs/최종정산.csv`는 차수 라벨에 은행서류 차수를 이미 병기해 두고 있다.

```
23 차(은행서류 24차)    24 차(은행서류 23차)
25 차(은행서류 27차)    27 차(은행서류 25차)
```

좌측 「LC 이자비용」 열만 **은행서류 차수 순**으로 적혀 우리 차수와 어긋난 것이고, 우측 「LC 정산 내역」의 **「수수료」가 정본**이다. 수수료 = 인수 + 이자, 여기에 우측 부대비용(개설·조건변경·기타)을 더하고 환급을 빼면 DB 부대비용 합계가 된다.

**DB는 이미 우측 기준으로 정확히 들어가 있다.**

| 차수 | 서류 우측 (수수료 + 부대비용 − 환급) | DB 부대비용 합계 | 판정 |
|---|---|---|---|
| 21차 | 1,716,258 | 1,716,258 | 일치 |
| 23차 | 3,471,200 | 3,467,397 | **−3,803** (2번 (나) 참조) |
| 24차 | 3,278,174 | 3,278,174 | 일치 |
| 27차 | 1,520,140 | 1,520,140 | 일치 |
| 28차 | 3,325,747 | 3,325,747 | 일치 |

**21·24·25·27·28차는 재입력 대상이 아니다.** 고칠 것은 23차 이자 한 줄뿐이다. 좌측 열은 읽지 말 것 — 24차 좌측 「LC 제비용 총합」 3,498,596은 좌우 어느 쪽과도 맞지 않는다.

## 5. 알려진 시스템 상태

### 감사 로그

- 트리거 **7개** 동작 중 — `transactions` / `interim_settlements` / `closing_settlements` / `lc_fee_items` / `closing_cost_items` / `interim_cost_items` / `containers` (마이그레이션 025 + 030)
  - 부모 3개만으로는 **LC수수료(`lc_fee_items`) 편집을 놓친다.** 13·17차 차이의 정체가 이것으로 추정된다
- `audit_logs` 는 앱에서 읽기 전용 — anon/authenticated의 INSERT/UPDATE/DELETE 회수됨. 트리거 함수는 SECURITY DEFINER라 기록은 계속된다
- **`AUTH_DISABLED` 때문에 `changed_by`는 항상 NULL.** 「무엇이 바뀌었나」만 남고 「누가」는 안 남는다
- ⚠️ **anon PostgREST로 `audit_logs`를 조회하지 말 것.** 항상 `200 + []`(0건)이 나온다 — 권한 거부가 아니라 RLS가 걸러낸 결과다
  - `audit_logs`는 **RLS가 켜진 유일한 테이블**이고(`relrowsecurity = true`), SELECT 정책이 `a1_admin can select audit_logs`(`authenticated` + `auth_role() = 'a1_admin'`) 하나뿐이다
  - 같은 이유로 앱의 감사 로그 화면(`app/(app)/audit-logs`)은 anon 클라이언트를 쓰는 한 **영원히 빈 화면**이다. 중복이던 `settings/audit` 화면과 쓰이지 않던 `app/api/audit-logs` 는 삭제했다 (2026-09-01)
  - **근본 해결은 로그인 복구(AUTH_RESTORE).** anon SELECT 정책을 여는 것은 공개 키를 가진 누구에게나 감사 이력을 여는 것이라 권하지 않는다
  - 건수 확인은 **SQL 에디터로만** 가능

- ⚠️ **항목 부가세를 공급가에 포함하던 규약은 2026-09-04 에 폐기됐다.** 그 시기의 커밋·아티팩트

## 8. 조사 방법 (재현용)

라이브 DB 대사는 아래 순서로 한다. **anon PostgREST로 조회 가능한 테이블**은 `transactions` / `interim_settlements` / `closing_settlements` / `lc_fee_items` / `closing_cost_items` 등 대부분이고, `audit_logs`와 `pg_catalog`만 SQL 에디터가 필요하다.

1. `.env.local`의 `NEXT_PUBLIC_SUPABASE_ANON_KEY`로 PostgREST 조회 (조인은 `transactions?select=...,closing_settlements(...)`)
2. `node ./scratch.ts` 로 `lib/calculations/` 의 함수를 **실제 코드 그대로** 돌려 재계산한다
3. DB 확정금액 − 재계산값으로 차이를 낸다

전 차수를 한 번에 훑느라 다른 언어로 공식을 다시 구현했다면, **결과를 반드시 화면 값과 대조할 것.**
공식을 두 번 쓰면 두 벌이 어긋나고, 어긋난 쪽이 보고서로 나간다.

통관 사실관계(입항일·수입신고일·선사·컨테이너번호·Master B/L)는 **관세청 유니패스 오픈API**로 확인한다.
`lib/tracking/unipass.ts`(화물통관진행정보) / `lib/tracking/customsRate.ts`(관세환율)를 그대로 쓰면 되고,
인증키는 `.env.local`의 `UNIPASS_API_KEY_CARGO` / `UNIPASS_API_KEY_FXRATE` 다.
**출항일(ETD)은 제공하지 않고, 보관주기 3년이 지난 건은 조회되지 않는다.**

DDL·`audit_logs`·카탈로그 조회는 SQL 에디터에서 실행해야 한다. **Supabase SQL 에디터는 여러 문장을 실행하면 마지막 문장의 결과만 보여준다** — 여러 조회를 한 번에 받으려면 `UNION ALL` 로 단일 SELECT를 만들 것.

- 담당자가 라이브 DB를 실시간으로 편집 중이다. 감사 결과는 스냅샷이므로 수치가 어긋나면 재조회한다 (예: 37차 항목 부가세가 152,470 → 156,180으로 변경된 사례)
- 확정금액을 바꾸는 SQL은 **실행 전 사용자에게 보여주고 승인받는다.** 금액이 큰 건(23차 5,780만원 등)은 담당자 컨펌까지 받는다
- 「확정금액 미갱신」 = 저장 후 LC수수료·결제비용·환율을 고쳤는데 확정금액이 재계산되지 않아 옛 값이 굳은 경우. 화면에서는 `OverrideMismatchNotice`가 경고와 되돌리기를 제공한다
- ⚠️ **2026-09-04 이전에 만든 대사 산출물(아티팩트·보고서·커밋 메시지)의 금액은 구규약 기준이다.**
  「항목 부가세 가산」이 들어간 분석은 전부 무효다. 숫자를 인용하기 전에 지금 화면 값과 대조할 것
- `fix_gross_customs_items.sql` 의 백업 테이블(`interim_cost_items_backup_20260904`)은 **비어 있다.**
  되돌리려면 `supabase/manual/restore_gross_customs_items.sql` 을 쓴다 (정정 전 스냅샷 62건)
