# 정산 현황 및 확정 규약

최종 갱신: 2026-08-31 (라이브 DB 전수 대조 기준)

세션마다 같은 조사를 반복하지 않기 위한 문서. 금액이 걸린 판단은 여기 먼저 확인한다.

## 확정된 계산 규약 (담당자 확인 완료)

### 중간정산

```
공급가 = 수입금액USD × (1 + 마진%) × 통관환율
       + 해상운임 + 통관비 전체
       + 항목 부가세          ← 국내 비용(트럭운송비 등)에 붙은 부가세
       − 수입부가세           ← 세관 납부분, 매입세액공제 대상
부가세 = 절사된 공급가 × 10%
합계   = 공급가 + 부가세
```

항목별로 부가세를 떼지 않고 **토에이 실지급액을 그대로 매입원가**로 잡는다. 세관에 낸 수입부가세만 공제로 회수하므로 그것만 뺀다.

### 최종정산(클로징)

```
환차손익 = 원금 × 통관환율 − LC 결제비용        (양수 = 환차익)
공급가   = ((LC 부대비용 − 환차손익) + 기타 미정산 비용(A+B+C)) × A1 부담비율
부가세   = 절사된 공급가 × 10%
합계     = 공급가 + 부가세
```

- **부호**: 지불 양수 / 환급 음수
- **A1 부담비율**: 34차까지 50%, 35차부터 100%
  - 35차 이후 클로징이 아직 없으므로 소급 변경 대상 없음. 기본값은 이미 100%
- **기타 미정산 비용(A+B+C)**: 담당자 확정대로 **부담비율을 곱한다**. 원본 문서는 이 항목만 부담비율 밖 전액으로 뒀는데 그게 오류였다
  - 코드 반영 완료 (2026-08-31, `lib/calculations/closing.ts`의 `a1ClosingCostsKrw`). 신·구방식 모두 적용
  - `closingCostsTotalKrw`(원금)는 항목 목록 표시용으로 남기고, 공급가에는 부담분만 들어간다
  - A+B+C ≠ 0 인 차수는 **1·2차뿐**(라이브 DB 전수 확인). 둘 다 재입력 대상이라 소급 작업 불필요

### 절사

- 0 방향 버림 = 절대값 기준 절사. 음수(환급)도 동일
- 절사는 **공급가**에 건다. 합계에 걸면 공급가 + 부가세 ≠ 합계가 되어 세금계산서가 안 맞는다
- 적용 시작: 중간정산 17차부터 / 최종정산 29차부터
- **소급하지 않는다.** 과거 차수는 저장된 정책 스냅샷 그대로 둔다
  - 소급 시 변동폭 −98 ~ +99원인데, 지금 문서와 정확히 맞는 차수(3·5·9·19차 등)가 오히려 틀어지고 이미 발행된 세금계산서와 어긋난다
  - 새 규칙은 신규 차수와 어차피 재확정할 차수(30·31·32차)에만 적용
  - 30·31·32차 `rounding_policy` 정리 완료 (2026-08-31). 이제 29~34차 전부 `floor_100`

## 알려진 시스템 상태

- **감사 로그 트리거 복구 완료 (2026-08-31)** — 025 + 신규 030을 라이브 DB에 적용. 트리거 7개(transactions / interim_settlements / closing_settlements / lc_fee_items / closing_cost_items / interim_cost_items / containers)가 걸렸고 `audit_logs`는 anon 쓰기 회수됨(읽기 전용)
  - 025의 3개만으로는 **LC수수료(`lc_fee_items`) 편집을 놓친다** — 24·32차 오염 유형이 정확히 이것이라 030으로 자식 테이블까지 확장했다
  - `AUTH_DISABLED` 때문에 `changed_by`는 항상 NULL. **「무엇이 바뀌었나」만 남고 「누가」는 안 남는다**
  - **`audit_logs`는 실제로 557건이 쌓여 있다** (2026-08-31 SQL 에디터 확인). transactions 308 / interim_settlements 129 / closing_settlements 120건. 트리거는 이전부터 동작 중이었고 **「감사 로그 0건」이라는 과거 진단은 anon 경로로 측정한 오류**였다
  - 따라서 **24·32·23차 오염의 출처를 추적할 수 있다** — `closing_settlements` UPDATE 67건에 확정금액 변경 이력이 남아 있다. 작업 5번의 출발점
  - **원인 확정** — `audit_logs`는 **RLS가 켜져 있는 유일한 테이블**이고(`relrowsecurity = true`), SELECT 정책이 `a1_admin can select audit_logs` (`authenticated` 역할 + `auth_role() = 'a1_admin'`) 하나뿐이다. anon용 정책이 없어 테이블 권한(`anon SELECT = true`)이 있어도 RLS가 전부 걸러낸다 → `200 + []`
  - 따라서 앱의 감사 로그 화면 3곳(`app/(app)/audit-logs`, `app/(app)/settings/audit`, `app/api/audit-logs`)은 anon 클라이언트를 쓰는 한 **영원히 빈 화면**이다. **근본 해결은 로그인 복구(AUTH_RESTORE)** — anon SELECT 정책을 여는 것은 공개 키를 가진 누구에게나 감사 이력을 여는 것이라 권하지 않는다
  - **anon PostgREST로 audit_logs 건수를 재지 말 것.** SQL 에디터로만 확인된다
- **`f2e2be3` 미배포** — 항목 부가세를 공급가에 포함하는 수정이 `feat/interim-supply-basis-and-override-guard` 브랜치에만 있고 main에 없다. 37차 「오류」(192,601,600 vs 192,757,800)의 정체가 이것
- **정산 방식(`vat_mode`) 전환 UI 없음** — 29~34차를 신방식으로 소급하려면 DB 직접 수정 또는 화면 추가 필요
- **LC 결제비용 선지급금 별도 환율 — 코드 완료 (2026-08-31)**. `closing_settlements.advance_payment_usd` / `advance_exchange_rate` 추가(마이그레이션 031, **라이브 DB 미적용**)
  - `LC결제비용 = round(선지급$ × 선지급환율) + round(잔액$ × 클로징환율)`. 구간별로 반올림해 더한다 — 은행이 구간별로 결제해 청구하므로 합계를 한 번에 환산하면 원 단위로 어긋난다
  - 1차 검산: `7,040 × 1156.4 + 53,760 × 1202.4 = 72,782,080` → DB 저장값과 정확히 일치. 회귀 테스트로 고정했다
  - 선지급금이 0·NULL이면 기존과 동일(총액 × 클로징환율) — 기존 정산 계산 불변
  - 가드: 선지급금 있는데 환율 미입력 / 선지급금 > 총액 → 저장 차단(코드 + DB CHECK 양쪽)
- **차수 라벨 연도 오류 다수** — 1~10·16·17·18·21·23·25·27·34차. 25·34차는 통관일이 LC개설일보다 빠름
