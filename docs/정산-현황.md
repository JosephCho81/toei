# 정산 현황 및 확정 규약

최종 갱신: 2026-08-31 · 라이브 DB 전수 대조 + 감사 로그 추적 + 담당자 보고 대조 완료 기준

세션마다 같은 조사를 반복하지 않기 위한 문서. **금액이 걸린 판단은 여기부터 확인한다.**

## 1. 확정된 계산 규약 (담당자 확인 완료)

### 중간정산

```
공급가 = 수입금액USD × (1 + 마진%) × 통관환율
       + 해상운임 + 통관비 전체
       + 항목 부가세          ← 국내 비용(트럭운송비 등)에 붙은 부가세
       − 수입부가세           ← 세관 납부분, 매입세액공제 대상
부가세 = 절사된 공급가 × 10%
합계   = 공급가 + 부가세
```

항목별로 부가세를 떼지 않고 **토에이 실지급액을 그대로 매입원가**로 잡는다. 세관에 낸 수입부가세만 공제로 회수하므로 그것만 뺀다.

### 최종정산(클로징)

```
환차손익 = 원금 × 통관환율 − LC 결제비용        (양수 = 환차익)
공급가   = ((LC 부대비용 − 환차손익) + 기타 미정산 비용(A+B+C)) × A1 부담비율
부가세   = 절사된 공급가 × 10%
합계     = 공급가 + 부가세
```

- **부호**: 지불 양수 / 환급 음수
- **A1 부담비율**: 34차까지 50%, 35차부터 100%. 35차 이후 클로징이 아직 없어 소급 대상 없음
- **기타 미정산 비용(A+B+C)에도 부담비율을 곱한다.** 원본 문서가 이 항목만 부담비율 밖 전액으로 둔 것이 오류였다
  - `lib/calculations/closing.ts`의 `a1ClosingCostsKrw`. 신·구방식 모두 적용
  - `closingCostsTotalKrw`(원금)는 항목 목록 표시용, 공급가에는 부담분만 들어간다
  - A+B+C ≠ 0 인 차수는 **1·2차뿐** (라이브 DB 전수 확인)

### LC 결제비용 — 선지급금 별도 환율

```
LC결제비용 = round(선지급$ × 선지급환율) + round(잔액$ × 클로징환율)
```

구간별로 반올림해 더한다. 은행이 구간별로 결제해 청구하므로 합계를 한 번에 환산하면 원 단위로 어긋난다.
선지급금이 0·NULL이면 기존과 동일(총액 × 클로징환율)이라 기존 정산 계산은 변하지 않는다.

### 절사

- 0 방향 버림 = 절대값 기준. 음수(환급)도 동일
- 절사는 **공급가**에 건다. 합계에 걸면 공급가 + 부가세 ≠ 합계가 되어 세금계산서가 안 맞는다
- 적용 시작: 중간정산 17차부터 / 최종정산 29차부터
- **소급하지 않는다.** 과거 차수는 저장된 정책 스냅샷 그대로 둔다
  - 소급 시 변동폭 −98 ~ +99원인데, 지금 문서와 정확히 맞는 차수(3·5·9·19차 등)가 오히려 틀어지고 이미 발행된 세금계산서와 어긋난다
  - 29~34차는 전부 `floor_100` 으로 정리 완료

### 23차 — 두 건이 겹쳐 있다

**(가) 확정금액 미갱신 — 5,781만원.** 원인은 감사 로그로 확정됐다. 08-23 INSERT 시 LC결제비용이 11,660,589원으로 잘못 들어갔고, 08-24에 116,773,626원으로 정정했으나 확정금액 −59,350,700원이 갱신되지 않았다.

**(나) 이자 입력값 −3,803원.** 이자에 클로징환율 1,392.40이 아니라 **1,390.40(24차 은행정산 환율)이 적용**됐다. $1,900.26 × 1,390.40 = 2,642,122 ≈ 저장값 2,642,119. 차수 혼재(3번)의 흔적이 이자 한 줄에 남은 것이다.

| | 개설 | 인수 | 이자 | 합계 |
|---|---|---|---|---|
| 서류 우측(정본) | 193,085 | 632,193 | 2,645,922 | **3,471,200** |
| DB 입력값 | 193,085 | 632,193 | 2,642,119 | 3,467,397 |

재계산값 (`calculateClosing` 실제 실행):

```
현재 DB       부대비용 3,467,397  환차익 6,264,715  →  확정 -1,538,525
(나) 정정 후   부대비용 3,471,200  환차익 6,264,715  →  확정 -1,536,433   (+2,092)
```

**(나)를 먼저 넣고 (가)의 목표값을 −1,536,433으로 잡는다.** 두 SQL은 한 트랜잭션으로 실행할 것 — 절사 소급 안 하므로 `rounding_policy`는 `none` 유지:

```sql
UPDATE lc_fee_items SET amount_krw = 2645922
 WHERE id = '64f88c44-fa8e-44aa-9d2f-e40b5a0f1898';   -- 23차 이자

UPDATE closing_settlements SET confirmed_amount_krw = -1536433, updated_at = now()
 WHERE id = 'fce21fc1-26c3-4902-92ad-9d549fabf5ef';
```

통관환율은 DB의 **1467.1이 맞다.** `최종정산.csv`의 「입고시 신고환율 1,467.00」은 반올림 표기이고, `중간정산.csv`의 총 수입비용 123,038,342원은 1467.1로만 나온다.

### 1·2차 재입력 시 값

부담비율 50% 적용: 1차 기타 미정산 44,000 → 22,000 / 2차 333,400 → 166,700. 규약대로의 값이므로 시스템 재계산값으로 맞추면 된다.

**단, 이 항목들을 클로징에 두는 것 자체가 재검토 대상이다 (담당자 컨펌 대기).** 담당자는 중간정산으로 옮기자고 제안했다 — 1차 운송추가운임 44,000(디머리지·대기료), 2차 통관보수료 182,600 + 검역수수료 110,000 + 운송추가운임 40,800 = 333,400. 성격상 통관·운송 실비가 맞다.

**옮기면 에이원 부담이 50% → 100%가 된다.** 클로징은 부담비율 50%가 걸리지만 중간정산 통관비는 전액 반영이기 때문이다. 실질 부담 증가분 **1차 +22,000 / 2차 +166,700** (부가세 별도). 담당자 보고에는 이 부담 증가가 언급돼 있지 않으므로 명시해서 확인받을 것. 컨펌 결과에 따라 재입력 방식이 갈린다.

A+B+C ≠ 0 인 차수는 1·2차뿐이므로 (라이브 DB 전수 확인) 영향 범위도 이 둘로 끝난다.

1차는 **선지급금 백필**도 함께 넣는다. 저장된 LC결제비용 72,782,080원은 클로징환율 1202.4로는 나오지 않고, 선지급금 7,040$에 1156.4를 적용하면 원 단위까지 맞는다(`7,040 × 1156.4 + 53,760 × 1202.4`). 금액 변동 없음.

```sql
UPDATE closing_settlements
   SET lc_payment_total_usd = 60800, advance_payment_usd = 7040, advance_exchange_rate = 1156.4
 WHERE id = '0afc9658-046c-413b-b66e-1d195af87550';
```

## 3. 원본 문서의 좌측 「LC 이자비용」 열 — 은행서류 차수 순으로 적혀 있다

**「복사 오류」가 아니었다.** `_source_docs/최종정산.csv`는 차수 라벨에 은행서류 차수를 이미 병기해 두고 있다.

```
23 차(은행서류 24차)    24 차(은행서류 23차)
25 차(은행서류 27차)    27 차(은행서류 25차)
```

좌측 「LC 이자비용」 열만 **은행서류 차수 순**으로 적혀 우리 차수와 어긋난 것이고, 우측 「LC 정산 내역」의 **「수수료」가 정본**이다. 수수료 = 인수 + 이자, 여기에 우측 부대비용(개설·조건변경·기타)을 더하고 환급을 빼면 DB 부대비용 합계가 된다.

**DB는 이미 우측 기준으로 정확히 들어가 있다.**

| 차수 | 서류 우측 (수수료 + 부대비용 − 환급) | DB 부대비용 합계 | 판정 |
|---|---|---|---|
| 21차 | 1,716,258 | 1,716,258 | 일치 |
| 23차 | 3,471,200 | 3,467,397 | **−3,803** (2번 (나) 참조) |
| 24차 | 3,278,174 | 3,278,174 | 일치 |
| 27차 | 1,520,140 | 1,520,140 | 일치 |
| 28차 | 3,325,747 | 3,325,747 | 일치 |

**21·24·25·27·28차는 재입력 대상이 아니다.** 고칠 것은 23차 이자 한 줄뿐이다. 좌측 열은 읽지 말 것 — 24차 좌측 「LC 제비용 총합」 3,498,596은 좌우 어느 쪽과도 맞지 않는다.

## 4. 알려진 시스템 상태

### 감사 로그

- 트리거 **7개** 동작 중 — `transactions` / `interim_settlements` / `closing_settlements` / `lc_fee_items` / `closing_cost_items` / `interim_cost_items` / `containers` (마이그레이션 025 + 030)
  - 부모 3개만으로는 **LC수수료(`lc_fee_items`) 편집을 놓친다.** 13·17차 차이의 정체가 이것으로 추정된다
- `audit_logs` 는 앱에서 읽기 전용 — anon/authenticated의 INSERT/UPDATE/DELETE 회수됨. 트리거 함수는 SECURITY DEFINER라 기록은 계속된다
- **`AUTH_DISABLED` 때문에 `changed_by`는 항상 NULL.** 「무엇이 바뀌었나」만 남고 「누가」는 안 남는다
- ⚠️ **anon PostgREST로 `audit_logs`를 조회하지 말 것.** 항상 `200 + []`(0건)이 나온다 — 권한 거부가 아니라 RLS가 걸러낸 결과다
  - `audit_logs`는 **RLS가 켜진 유일한 테이블**이고(`relrowsecurity = true`), SELECT 정책이 `a1_admin can select audit_logs`(`authenticated` + `auth_role() = 'a1_admin'`) 하나뿐이다
  - 같은 이유로 앱의 감사 로그 화면 3곳(`app/(app)/audit-logs`, `app/(app)/settings/audit`, `app/api/audit-logs`)은 anon 클라이언트를 쓰는 한 **영원히 빈 화면**이다
  - **근본 해결은 로그인 복구(AUTH_RESTORE).** anon SELECT 정책을 여는 것은 공개 키를 가진 누구에게나 감사 이력을 여는 것이라 권하지 않는다
  - 건수 확인은 **SQL 에디터로만** 가능

### 그 외

- ✅ **`f2e2be3` 배포 완료** — 항목 부가세를 공급가에 포함하는 수정은 `origin/main`에 들어가 있다(`feat/interim-supply-basis-and-override-guard` 브랜치는 이미 머지됐고 오히려 main보다 뒤처져 있다). **「미배포」로 적혀 있던 것이 오류였다**
  - 다만 37차 중간정산은 여전히 **−44,880** 차이가 남아 있고 원인이 다르다. 저장된 공급가 192,717,000은 트럭운송비 부가세 115,370만 반영하고 **통관보수료·검역수수료 부가세 40,810이 빠져 있다.** 규약대로면 항목 부가세 156,180 전액이 들어가 공급가 192,757,800 / 합계 212,033,580이 맞다
  - 35~43차 중간정산 재계산 결과 **37차를 뺀 전부가 차이 0**
- **정산 방식(`vat_mode`) 전환 UI 없음** — 라이브 DB의 클로징 33건이 전부 `inclusive`다. 29~34차를 신방식으로 소급하려면 DB 직접 수정 또는 화면 추가 필요
- **차수 라벨 연도 오류 다수** — 1~10·16·17·18·21·23·25·27·34차. 25·34차는 통관일이 LC개설일보다 빠름

## 6. 남은 작업

### 담당자 컨펌 대기

1. **23차 정정** — 이자 2,642,119 → 2,645,922 + 확정금액 −59,350,700 → −1,536,433 (위 2번 SQL 2문)
2. **1·2차 기타 미정산 비용을 중간정산으로 옮길지** — 옮기면 에이원 부담 50% → 100%(1차 +22,000 / 2차 +166,700). 답이 나와야 1·2차 재입력 방식이 정해진다

### 컨펌 불필요 — 사용자 승인만 받으면 실행

3. **6차 확정금액** −100, **37차 확정금액** −44,880 — 둘 다 시스템이 맞다. 확정금액만 맞추면 끝
4. **1차 선지급금 백필** — 금액 변동 없음 (위 2번 SQL)

### 서류 대기

5. **7차 원인 규명** — 원본 서류 수령 후. 1~10차 재입력 요청에 **7차를 명시적으로 포함**시킬 것
6. **20·25·42차 서류** — 25차는 22차 자료가 잘못 와 있어 재요청 중. 44차는 9월 말 입항 이후

### 선택

7. **로그인 복구(AUTH_RESTORE)** — 감사 로그 화면을 살리려면 필요. RLS를 켜면 앱이 즉시 죽으므로 반드시 같이 해야 한다

## 7. 조사 방법 (재현용)

라이브 DB 대사는 아래 순서로 한다. **anon PostgREST로 조회 가능한 테이블**은 `transactions` / `interim_settlements` / `closing_settlements` / `lc_fee_items` / `closing_cost_items` 등 대부분이고, `audit_logs`와 `pg_catalog`만 SQL 에디터가 필요하다.

1. `.env.local`의 `NEXT_PUBLIC_SUPABASE_ANON_KEY`로 PostgREST 조회 (조인은 `transactions?select=...,closing_settlements(...)`)
2. `node ./scratch.ts` 로 `lib/calculations/closing.ts`의 `calculateClosing`을 **실제 코드 그대로** 돌려 재계산 — 파이썬으로 공식을 다시 구현하지 말 것
3. DB 확정금액 − 재계산값으로 차이를 낸다

DDL·`audit_logs`·카탈로그 조회는 SQL 에디터에서 실행해야 한다. **Supabase SQL 에디터는 여러 문장을 실행하면 마지막 문장의 결과만 보여준다** — 여러 조회를 한 번에 받으려면 `UNION ALL` 로 단일 SELECT를 만들 것.

## 8. 유의

- 담당자가 라이브 DB를 실시간으로 편집 중이다. 감사 결과는 스냅샷이므로 수치가 어긋나면 재조회한다 (예: 37차 항목 부가세가 152,470 → 156,180으로 변경된 사례)
- 확정금액을 바꾸는 SQL은 **실행 전 사용자에게 보여주고 승인받는다.** 금액이 큰 건(23차 5,780만원 등)은 담당자 컨펌까지 받는다
- 「확정금액 미갱신」 = 저장 후 LC수수료·결제비용·환율을 고쳤는데 확정금액이 재계산되지 않아 옛 값이 굳은 경우. 화면에서는 `OverrideMismatchNotice`가 경고와 되돌리기를 제공한다
