# 화면 규칙 — 어기면 화면이 다시 어지러워진다

> **언제 읽나**: 화면을 고치거나 열·카드·색을 더하기 전.

## 화면 구성

화면마다 답하는 질문이 다르다. **같은 값을 여러 화면에 늘리지 말 것.**

**첫 화면은 지급 현황이다** — `/` 와 `/(app)` 은 `/payments` 로 보낸다(로그인 복원 후에도 동일).

**왼쪽 메뉴는 다섯 칸뿐이다 (2026-09-05).** 같은 질문을 대상만 바꿔 묻는 화면은
사이드바에 늘어놓지 않고 **화면 안 탭**이 가른다 — 사이드바에 또 세우면 그 탭 바를
그대로 복제하는 꼴이 된다.

| 메뉴 | 안에서 갈리는 것 | 가르는 곳 |
|---|---|---|
| 정산 비교 | 중간 · 최종 · 지체상금 | `CompareScreen` 탭 |
| 기준정보 | 제조사 · 품목 마스터 | `MasterTabs` |

- 사이드바 활성 표시는 `navItems[].match` 접두사로 넓힌다. 탭으로 옆 화면에 가도 메뉴가 꺼지면 안 된다
- **`/containers` 는 삭제했다 (2026-09-05).** 등록·수정이 거래 상세에서만 되는 읽기 전용
  복제 표였다 — 선박명·추적상태까지 포함해 `ContainerList`(거래 상세)가 이미 더 많이 보여준다.
  다시 만들지 말 것
- **검증 리포트(`/verification`)는 라우트만 남기고 메뉴에서 뺐다.** 원본문서↔DB 적재 QA 도구지
  운영 화면이 아니다. 지급 현황(`PaymentTable`)의 링크로 들어간다

| | 답하는 질문 | 독자 |
|---|---|---|
| **지급 현황** (`/payments`) | 돈이 실제로 오갔나, 얼마가 남았나 | 양사 대표 · 기본 읽기 전용 |
| **중간·최종·지체상금** (`/settlements/*`) | 청구가 계산과 맞나, 어디가 얼마나 어긋났나 | 담당자 · 대사 |
| **정산 현황** (`/dashboard`) | 돈이 언제 오가나, 무엇이 늦었나 | 담당자 · 물류·정산 일정 |
| **거래 목록** (`/transactions`) | 무엇을 얼마에 샀나, 어디가 틀렸나 | 담당자 · 품목·금액 대조 |

#### 금액이 셋이다 — 섞지 말 것

`/settlements/*` 세 화면이 생긴 이유다. 같은 차수에 금액이 셋 있고 뜻이 다르다.

| | 뜻 | 어디 |
|---|---|---|
| **청구액** `invoiced_amount_krw` | 실제로 청구서에 적어 보낸 금액 (사실) | 중간 `035` / 최종 `038` |
| **확정금액** `confirmed_amount_krw` | 담당자가 확정한 금액 (판단) | 저장됨 |
| **계산값** | 현재 규약으로 다시 계산 (`calculateInterim`/`calculateClosing`) | **저장하지 않는다** |

그래서 차이도 둘이다. **「청구 − 계산」은 청구가 틀린 것**이고 **「청구 − 지급」은 아직 안 낸 것**이다.
2026-09-04 이전에는 지급 현황이 청구↔지급만, 검증 리포트가 확정↔재계산만 봐서
**35차처럼 「계산은 맞는데 청구만 554만원 적게 나간」 건이 어느 화면에도 보이지 않았다.**

- 계산값을 저장하지 말 것 — 저장하는 순간 규약이 바뀌어도 화면은 옛 규약을 말한다
- 구방식(`vat_mode = 'inclusive'`) 정산은 「덜/더 청구」 집계에서 뺀다. 넣으면 2·6·7차의
  부가세 구조 차이가 3,400만원짜리 청구 오류처럼 보인다
- 읽기 실패를 삼키지 말 것 — 마이그레이션이 안 올라간 화면이 「정산이 하나도 없습니다」라고
  말하면 44개 차수가 사라진 것과 진짜 빈 화면을 구분할 수 없다. 오류 메시지를 그대로 띄운다
- 지체상금은 **산식이 없다.** 담당자가 적은 금액이 곧 청구액이다 (`037`). 지어내지 말 것

#### 정산 3화면은 한 벌이다

`/settlements/interim` · `closing` · `penalty` 가 **같은 표 컴포넌트**를 쓴다
(`CompareScreen` + `CompareTable`, 데이터는 `lib/data/settlementCompare.ts`).
셋을 나눈 이유는 항목이 많아서가 아니라 **읽는 질문이 같고 대상만 다르기 때문**이다 —
한 화면에 몰면 44행 × 3구분이 되어 차수를 눈으로 좇을 수 없다.

- 열: `선택 · 차수·P/O · 수입금액($) · 청구금액 · 계산금액 · 계산 차이 · 실지급액 · 청구-지급 차이 · 계산-지급 차이 · 기일 · 비고`
  (담당자 양식 2026-09-10). **실지급일은 펼침으로 내렸다** — 표에는 청구 기일만 선다
- **청구액은 여기서 적어 넣는다.** 줄을 펴면 입력칸이 있고 `interim_settlements` ·
  `closing_settlements` 의 `invoiced_amount_krw` 에 쓴다. 흐름은
  「직원 검수 → 최차장님 검토 → 계산서 검토 → 입력」이다(담당자 2026-09-10).
  **계산값을 그대로 굳히는 버튼을 두지 말 것** — 복사해 넣으면 둘의 차이가 영원히 0 이 되어
  이 표가 답해야 할 질문 자체가 사라진다. 계산서 발행에서 생기는 10원 단위 차이는
  1,000원 미만 허용치가 이미 걸러낸다
- **차이 열이 셋이다.** 「청구−계산」(청구서가 틀림) · 「청구−지급」(아직 안 냄) ·
  「계산−지급」(청구가 맞았다면 남았을 돈). 합치면 35차 같은 건을 못 찾는다
- 왼쪽 체크박스로 **임의 구간 합계**를 낸다 — 담당자 양식의 「35차까지」와
  E열(8·9·10차 합산)이 이걸로 해결된다. 소계·총계·선택 합계는 전부 `aggregate()` 하나를 쓴다
- **연도(기일 기준) 소계와 총 합계**가 표 안에 선다
- 「합산지불」은 사람이 체크하지 않는다 — 이체 1건에 배분이 여러 차수면 원장이 이미 안다
  (`markMergedPayments()` 가 「N차와 묶음 지급」으로 붙인다)
- **비고(메모)** 는 `interim_settlements.notes` · `closing_settlements.notes` ·
  `settlement_penalties.note` 에 그대로 쓴다. 새 컬럼을 만들지 말 것 — 이미 있다.
  시스템이 차이의 원인을 지어내지 않는다. 금액만 나란히 세우고 이유는 사람이 적는다
- 줄을 펴면 네 금액(청구·확정·계산·지급)이 나란히 서고 **왜 어긋났는지 한 문장**이 붙는다
- 지급 입력은 여기서 하지 않는다 — 지급 현황 한 곳뿐이다
- 첫 화면(지급 현황)에는 **세 구분 한 줄 요약**만 둔다(`KindSummary`).
  여기에 「청구−계산」을 끌어오면 대표 첫 화면이 다시 대사표가 된다

- 정산 현황 컬럼: 회차 · 제조사 · 수입금액 · B/L · ETD · ETA · LC개설 · 중간정산 · 최종정산 · 상태
- 거래 목록 컬럼: 오류 · 회차 · P/O No. · 제조사 · 품목(펼침) · ETA · 상태

- 물류·정산 일정은 **정산 현황**이 담당한다. 거래 목록에서 LC 개설일·ETD 를 뺐다.
- ETA 만 양쪽에 있다 — 거래 목록 쪽은 `getEtaDisplay()` 로 컨테이너 ETA 가 없으면
  인도일(`delivery_dates`)로 대체해 보여주므로 같은 값이 아니다.
- 겹치는 회차·제조사·상태는 행을 식별하는 데 필요해 남긴다.
