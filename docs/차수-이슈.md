# 차수별 미해결 건

> **언제 읽나**: 특정 차수의 금액이 안 맞을 때. **차수 번호로 `grep` 해서 그 절만 읽을 것.**

## 확정금액 재입력 — 37개 차수 (2026-09-04 소급 이후)

**「확정금액 − 계산값」이 지금 전 차수에서 양수인 것은 오류가 아니다.** 09-04 계산식 개정을
소급 적용해 계산값이 내려갔는데 `confirmed_amount_krw` 는 옛 규약 값 그대로이기 때문이다.
담당자가 재검토하며 넣으면 0이 된다 — **자동 갱신하지 않는다.**

차이가 1,000원 이상인 차수 **37개**. 큰 것부터:

| 차수 | 확정 − 계산 | 차수 | 확정 − 계산 |
|---|---|---|---|
| 1차 | +389,670 | 34차 | +193,130 |
| 43차 | +283,440 | 37차 | +126,940 |
| 17차 | +211,420 | 20차 | +118,800 |
| 28차 | +115,830 | 23차 | +115,060 |

나머지 29개는 +27,280 ~ +110,550 범위다. **차이 0인 차수는 6·7·9·10차**뿐이다
(6·7차는 구방식이라 계산이 바뀌지 않았고, 9·10차는 우연히 맞는다).

화면의 「계산값」 열이 넣어야 할 목표값이다 — `/settlements/interim`.

### 담당자 수기검산 대조 (2026-09-05, 라이브 DB)

담당자가 보낸 숫자를 그대로 재현해 봤다. **청구·지급은 완전히 일치한다.**

| 기준 (1~35차, 2·3차 제외) | 금액 |
|---|---|
| 청구 누계 | 3,156,778,502 |
| 지급 누계 | 3,157,463,987 |
| **청구 − 지급** | **−685,485 (더 지급)** ← 담당자 「약 68만 더 지급」과 일치 |

**계산 기준은 아직 안 맞는다.** 담당자는 「300 정도 덜 지급」이라 했는데 우리 값은 이렇게 갈린다.

| 기준 | 계산 − 지급 |
|---|---|
| 1~35차 (2·3차 제외) | 17,083,922 더 지급 |
| ↑ 6·7차(구방식) 제외 | 5,779,513 덜 지급 |
| ↑ 35차(오기입 건) 제외 | 295,738 덜 지급 |

「300」이 **30만**이면 마지막 줄과 맞고, **300만**이면 담당자 기준에 우리와 다른 지점이
하나 더 있다. **확인 필요.**

#### 35차 청구 오차는 담당자 지목대로 전액 설명된다

담당자 메모 예시(「오기입 2건 — 통관환율 실 1479.34 / 입력 1439.26, 배송비 실 약 177만 /
입력 약 17만」)를 검증했다. **DB 는 이미 정정된 값을 들고 있다** (환율 1479.34,
운송비 항목 합계 1,745,085). 두 오기입의 영향을 되짚으면

```
(80,497.5 × 1.05 × 40.08) + (1,745,085 − 170,000) = 4,962,742
4,962,742 × 1.1 = 5,459,016
```

화면의 35차 「청구−계산」은 **−5,483,717**. 차이 24,701원(절사·배송비 어림값)뿐이라
**청구서가 틀린 것이 맞다.** 확정금액이 계산값과 일치하므로 계산 문제가 아니다.

### 구방식(`inclusive`) 잔존 3건 — 2·6·7차뿐이다

라이브 DB 중간정산 41건 중 이 셋만 `inclusive` 다. 원본 CSV 마지막 열이
「+ 부가세 제외(7%)」= 공급가인데 그 값이 그대로 확정금액이 되어 **매출부가세 10%가 빠졌다.**

신규약은 구방식을 손대지 않는다 — 부가세를 분리할 수 없어 관세만 빼면 합계가 어긋난다.
**재입력하면 자동으로 `exclusive` 로 넘어가고 확정금액이 크게 뛴다**(각 +1,100만~1,200만).
이미 발행된 세금계산서와의 정합을 먼저 확인할 것. 담당자 재입력 대상(1~10차)에 포함돼 있다.

6·7차 수입부가세(6차 10,530,210 / 7차 10,751,980)는 아직 적재하지 않았다 —
`exclusive` 전환과 **반드시 같이** 넣어야 한다. 구방식은 비용을 빼지 않고 전부 더하므로
지금 넣으면 그대로 공급가에 얹힌다.

### 23차 클로징 — 아직 그대로다 (확정 −59,350,700)

**(가) 확정금액 미갱신 — 5,781만원.** 감사 로그로 확정됐다. 08-23 INSERT 시 LC결제비용이
11,660,589원으로 잘못 들어갔고, 08-24에 116,773,626원으로 정정했으나 확정금액이 갱신되지 않았다.

**(나) 이자 입력값 −3,803원.** 이자에 클로징환율 1,392.40이 아니라
**1,390.40(24차 은행정산 환율)이 적용**됐다. $1,900.26 × 1,390.40 = 2,642,122 ≈ 저장값 2,642,119.

| | 개설 | 인수 | 이자 | 합계 |
|---|---|---|---|---|
| 서류 우측(정본) | 193,085 | 632,193 | 2,645,922 | **3,471,200** |
| DB 입력값 | 193,085 | 632,193 | 2,642,119 | 3,467,397 |

**(나)를 먼저 넣고 (가)의 목표값을 −1,536,433으로 잡는다.** 두 SQL은 한 트랜잭션으로 —
절사 소급 안 하므로 `rounding_policy` 는 `none` 유지:

```sql
UPDATE lc_fee_items SET amount_krw = 2645922
 WHERE id = '64f88c44-fa8e-44aa-9d2f-e40b5a0f1898';   -- 23차 이자

UPDATE closing_settlements SET confirmed_amount_krw = -1536433, updated_at = now()
 WHERE id = 'fce21fc1-26c3-4902-92ad-9d549fabf5ef';
```

통관환율은 DB의 **1467.1이 맞다.** `최종정산.csv` 의 「입고시 신고환율 1,467.00」은 반올림 표기이고,
`중간정산.csv` 의 총 수입비용 123,038,342원은 1467.1로만 나온다.

### 6·7차 중간정산 종결 (2026-09-01)

| 차수 | 원인 | 조치 | 확정금액 |
|---|---|---|---|
| 6차 | 통관 항목(통관보수료 173,800 + 검역 110,000) 미적재 | 원본 값으로 적재 + 확정금액 갱신 | 113,128,700 |
| 7차 | 위 + **`import_amount_usd` 에 8차 값 75,829.5가 복사**돼 있었다 | 79,200으로 정정 + 통관 항목 적재 | 115,504,800 |

7차 재계산값이 원본 문서 115,504,856의 절사값과 정확히 일치한다 — USD 오입력이 맞았다는 증거다.
되돌릴 값은 6차 112,844,900 / 7차 115,217,700.

### 5차 — 트럭비 하나뿐 (서류 대기)

담당자 수기값 106,306,517과의 차이는 **트럭비 319,000과 절사뿐**이다. DB 5차는 원본 CSV와
완전 일치하고 **트럭비는 원본 문서에도 없다** — 서류 누락이다.
5·6·7차 트럭비를 넣는다면 **부가세 제외 금액**으로 넣는다(5차 290,000 / 6차 810,000 / 7차 308,000).

### 37차 — 수입금액 기준과 과세환율 2건

**신고가 2건이고 과세환율이 서로 다르다** (2026-09-02 유니패스 확인).

| B/L | 컨테이너 | 카톤 | 수입신고번호 | 신고일 | 고시환율 |
|---|---|---|---|---|---|
| KULFE2600**429** | NSSU7161942 | 3,760 | 02012014260180893A | 2026-05-29 | **1504.04** |
| KULFE2600**428** | NSSU0215292 | 1,380 | 02012014260180889A | 2026-06-01 | **1507.15** |

DB `customs_exchange_rate` 는 1504.04 하나뿐이다 — **429 기준**이고 428분에는 1507.15가 적용됐어야 한다.
카톤 비율(1,380/5,140 = 26.85%)로 추정한 영향은 **약 11.5만원**이나, 카톤 수와 금액 비율이
같다는 보장이 없어 **추정치**다. 신고필증 428·429의 과세가격을 봐야 확정된다.

구조적으로 `transactions.customs_exchange_rate` 가 차수당 1개라 **한 차수에 신고 2건이고
환율이 갈리면 표현할 방법이 없다.** 서류 확인 후 스키마를 손댈지 판단한다.

수입금액도 DB 119,412$(수기금액) vs 통관금액 119,452$ 로 **40$ 차이**(≈63,170원)가 남아 있다.

### 1·2차 클로징 — 부담비율 재입력

부담비율 50% 적용: 1차 기타 미정산 44,000 → 22,000 / 2차 333,400 → 166,700.
현재 클로징 확정은 1차 −180,400 / 2차 6,669,400.

**단, 이 항목들을 클로징에 두는 것 자체가 재검토 대상이다.** 담당자는 중간정산으로 옮기자고
제안했다 — 1차 운송추가운임 44,000(디머리지·대기료), 2차 통관보수료 182,600 + 검역수수료 110,000
+ 운송추가운임 40,800 = 333,400. 성격상 통관·운송 실비가 맞다.
**옮기면 에이원 부담이 50% → 100%가 된다**(1차 +22,000 / 2차 +166,700, 부가세 별도).
A+B+C ≠ 0 인 차수는 1·2차뿐이라 영향 범위도 이 둘로 끝난다.

1차는 **선지급금 백필**도 함께 넣는다. 저장된 LC결제비용 72,782,080원은 클로징환율 1202.4로는
나오지 않고, 선지급금 7,040$에 1156.4를 적용하면 원 단위까지 맞는다. 금액 변동 없음:

```sql
UPDATE closing_settlements
   SET lc_payment_total_usd = 60800, advance_payment_usd = 7040, advance_exchange_rate = 1156.4
 WHERE id = '0afc9658-046c-413b-b66e-1d195af87550';
```

## 원본 문서의 좌측 「LC 이자비용」 열 — 은행서류 차수 순으로 적혀 있다

**원본을 복사하다 밀린 것이 아니다.** `_source_docs/최종정산.csv`는 차수 라벨에 은행서류 차수를 이미 병기해 두고 있다.

```
23 차(은행서류 24차)    24 차(은행서류 23차)
25 차(은행서류 27차)    27 차(은행서류 25차)
```

좌측 「LC 이자비용」 열만 **은행서류 차수 순**으로 적혀 우리 차수와 어긋난 것이고, 우측 「LC 정산 내역」의 **「수수료」가 정본**이다. 수수료 = 인수 + 이자, 여기에 우측 부대비용(개설·조건변경·기타)을 더하고 환급을 빼면 DB 부대비용 합계가 된다.

**DB는 이미 우측 기준으로 정확히 들어가 있다.**

| 차수 | 서류 우측 (수수료 + 부대비용 − 환급) | DB 부대비용 합계 | 판정 |
|---|---|---|---|
| 21차 | 1,716,258 | 1,716,258 | 일치 |
| 23차 | 3,471,200 | 3,467,397 | **−3,803** (2번 (나) 참조) |
| 24차 | 3,278,174 | 3,278,174 | 일치 |
| 27차 | 1,520,140 | 1,520,140 | 일치 |
| 28차 | 3,325,747 | 3,325,747 | 일치 |

**21·24·25·27·28차는 재입력 대상이 아니다.** 고칠 것은 23차 이자 한 줄뿐이다. 좌측 열은 읽지 말 것 — 24차 좌측 「LC 제비용 총합」 3,498,596은 좌우 어느 쪽과도 맞지 않는다.
