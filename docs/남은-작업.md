# 남은 작업

> **언제 읽나**: 「지금 뭐가 남았나」를 물을 때. 진행 상황이 바뀌면 여기부터 고친다.

## 진행 현황 (2026-09-10 기준)

### 담당자 진행 중

1. **확정금액 재입력 37개 차수** — 09-04 소급 미반영분. 화면 「계산값」 열이 목표값이다 (`docs/차수-이슈.md`)
2. **1~10차 재입력** — 서류 미비 보완. 2차 통관보수 누락 / 5·6·7차 트럭비 누락.
   **2·6·7차는 구방식이라 재입력 시 확정금액이 +1,100만~1,200만씩 뛴다** — 세금계산서 정합 확인이 먼저다
3. **35·38·39차 원본 청구서** — 실제 청구가 계산보다 각각 −5,483,717 / −1,164,056 / −1,169,556.
   35차는 확정금액이 계산값과 일치하므로 **계산이 아니라 청구가 틀린 건**이고,
   38·39차는 금액이 거의 같아 같은 원인으로 보인다. 셋 합쳐 약 780만원
4. **20·25·42차 서류** — 25차는 22차 자료가 잘못 와 있어 재요청 중. 44차는 입항 이후
5. **지체상금 입력** — `/settlements/penalty` 에서 수기 입력. 산식은 미확정.
   통장 원장에 지체상금으로 보이는 기록이 5건 있다(「영업수수료(실제 지체상금)」 4건 5,046,032원
   + 상계된 5,666,612원). 이걸 지체상금 항목으로 옮길지 판단 필요
6. **최종정산 실제 청구액** — `038` 로 칸만 만들었고 **33건 전부 비어 있다.**
   값이 없어 최종정산 화면이 전부 「청구 전」이다.
   **입력칸은 2026-09-10 에 만들었다** — 정산 비교 화면에서 차수를 펴면 나온다
7. **중간정산 36~39차 청구값** — 엑셀값을 비웠으므로 검수 후 같은 자리에 넣는다.
   넣기 전까지는 계산값이 잔액 기준이다
8. **2·3차 지급 기록** — 개인 통장 등으로 이미 나갔다는 담당자 확인이 있다.
   실제 지급일과 금액을 받으면 지급금 차이가 161,821,438 → 697,597 로 줄어든다

### 사용자 승인만 받으면 실행

7. **23차 정정** — 이자 2,642,119 → 2,645,922 + 확정금액 −59,350,700 → −1,536,433 (2번 SQL 2문).
   금액이 커서 담당자 컨펌까지 받을 것
8. **1차 선지급금 백필** — 금액 변동 없음 (2번 SQL)

### 서류 대기

9. **7차 클로징 원인 규명** — 현재 확정 −1,330,400. 중간정산 쪽은 USD 오입력 정정으로 종결
10. **37차 신고필증 428·429** — 수입금액 40$ 차이와 과세환율 2건 분리(약 11.5만원) 확정용 (`docs/차수-이슈.md` 37차)
11. **Master B/L 3종의 선사 확인** — `HASL…`(2차·5차) / `EASB…`(2건) / `JCSC…`(1건).
    알려주면 `lib/tracking/carriers.ts` 에 추가한다. **URL 을 추측해 넣지 말 것** —
    `verified` 필드는 실제 접속 확인을 뜻한다. `HASL` 2건은 2022년 건이라 유니패스 3년을 넘겨 조회되지 않는다
12. **Master B/L 없는 4건** — `KULFE2600119` · `KULFE240076` · `KULFE2201819` · `KULFE2201818`.
    거래 상세에서 유니패스 조회를 한 번 돌리면 채워진다. 2022년 2건은 조회되지 않을 수 있다

### 선택

13. **로그인 복구(AUTH_RESTORE)** — 감사 로그 화면을 살리려면 필요. RLS를 켜면 앱이 즉시 죽으므로 반드시 같이 해야 한다
