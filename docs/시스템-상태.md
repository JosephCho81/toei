# 시스템 상태와 함정

> **언제 읽나**: DB를 조회·수정하기 전, 또는 계산이 화면과 어긋날 때.

## 계산 코드 정합 — 2026-09-01 전수 점검

**규약의 원본은 `lib/calculations/` 다.** 엑셀·원본 문서가 아니라 이 코드가 기준이고,
화면·PDF·대시보드는 여기를 **호출만** 해야 한다. 공식을 다시 쓴 곳에서 실제로 차이가 나 있었다.

| 위치 | 무엇이 틀렸나 | 조치 |
|---|---|---|
| `lib/data/dashboard.ts` 검증 이슈 차액 | `(수입금액 + 비용합계) × 1.10` 으로 재계산 — **항목 부가세·수입부가세 공제·절사 정책·`vat_mode` 를 전부 무시**했다. 규약대로 저장된 차수도 차액이 있는 것처럼 떴다 | `calculateInterim` 호출로 교체 (`lib/calculations/settlementDiff.ts` + 회귀 테스트 6건) |
| `lib/pdf/ClosingPdfTemplate.tsx` 환율 민감도 표 | LC 결제액 대신 **수입금액USD** 로 환산했고, `round(부담분 × 1.1) + 기타비용` 이라는 **구방식 공식이 박혀** 있었다. 절사·`vat_mode` 도 무시 | `calculateClosing` 호출로 교체 (`lib/pdf/closingSensitivity.ts` + 회귀 테스트 8건) |
| `components/report/ReportInterimSection.tsx` | 공급가 대체 계산식이 `calculateInterim` 과 어긋나 있었다 | `interimSummary.ts` 가 같은 규약을 따르도록 통일 |
| `lib/pdf/InterimPdfTemplate.tsx` 원가 계산표 | 나열한 항목을 다 더해도 아래 「공급가」가 안 나왔다 | 차감 줄(수입부가세·관세)을 넣어 합이 맞게 했다 (`lib/pdf/interimRows.ts` + 회귀 테스트 7건) |

| `app/(app)/verification/page.tsx` | 대상 차수가 **`rn <= 33` 으로 하드코딩** — 34차 이후가 조용히 빠졌다 | `source_documents` 에 적재된 차수 전부로 변경 |

### 계산에 쓰이지 않던 입력값

`closing_cost_items.includes_vat`(화면의 「부가세 포함」 체크)는 **`calculateClosing` 이 읽지 않는다.**
규약(`기타 미정산 비용 × 부담비율`)에 그 구분이 없어서 테스트도 전액 포함을 기대하고 있다.
계산 시그니처에서는 뺐고 DB 컬럼과 체크박스는 기록용으로 남겼다.
**체크가 금액을 바꾸지 않는다는 점을 담당자에게 알릴 것** — 바꿔야 한다면 규약부터 정해야 한다.

## 알려진 시스템 상태

### 감사 로그

- 트리거 **7개** 동작 중 — `transactions` / `interim_settlements` / `closing_settlements` / `lc_fee_items` / `closing_cost_items` / `interim_cost_items` / `containers` (마이그레이션 025 + 030)
  - 부모 3개만으로는 **LC수수료(`lc_fee_items`) 편집을 놓친다.** 13·17차 차이의 정체가 이것으로 추정된다
- `audit_logs` 는 앱에서 읽기 전용 — anon/authenticated의 INSERT/UPDATE/DELETE 회수됨. 트리거 함수는 SECURITY DEFINER라 기록은 계속된다
- **`AUTH_DISABLED` 때문에 `changed_by`는 항상 NULL.** 「무엇이 바뀌었나」만 남고 「누가」는 안 남는다
- ⚠️ **anon PostgREST로 `audit_logs`를 조회하지 말 것.** 항상 `200 + []`(0건)이 나온다 — 권한 거부가 아니라 RLS가 걸러낸 결과다
  - `audit_logs`는 **RLS가 켜진 유일한 테이블**이고(`relrowsecurity = true`), SELECT 정책이 `a1_admin can select audit_logs`(`authenticated` + `auth_role() = 'a1_admin'`) 하나뿐이다
  - 같은 이유로 앱의 감사 로그 화면(`app/(app)/audit-logs`)은 anon 클라이언트를 쓰는 한 **영원히 빈 화면**이다. 중복이던 `settings/audit` 화면과 쓰이지 않던 `app/api/audit-logs` 는 삭제했다 (2026-09-01)
  - **근본 해결은 로그인 복구(AUTH_RESTORE).** anon SELECT 정책을 여는 것은 공개 키를 가진 누구에게나 감사 이력을 여는 것이라 권하지 않는다
  - 건수 확인은 **SQL 에디터로만** 가능

### 그 외

- ⚠️ **항목 부가세를 공급가에 포함하던 규약은 2026-09-04 에 폐기됐다.** 그 시기의 커밋·아티팩트
  (`f2e2be3`, 「5·6·7·37차 차액 대사」 등)에 남은 「항목 부가세 가산」 분석은 **더 이상 유효하지 않다.**
  37차의 −44,880(통관보수료·검역수수료 부가세 40,810 미반영) 분석도 같이 무효다
- **정산 방식(`vat_mode`) 전환 UI 없음** — 라이브 DB의 클로징 **33건이 전부 `inclusive`**,
  중간정산은 2·6·7차만 `inclusive` 다. 전환은 DB 직접 수정 또는 재입력으로만 된다
- ⚠️ **정산 잠금(`is_locked`)은 화면에서만 걸린다.** 018 마이그레이션의 잠금 정책은 RLS 정책인데 `interim_cost_items` 는 RLS가 꺼져 있어 무력하다 — 확정된 정산도 PostgREST로는 항목이 그대로 수정된다
- **차수 라벨 연도 오류 다수** — 1~10·16·17·18·21·23·25·27·34차. 라벨만의 문제이고 금액과는 무관하다
  - 34차 통관일 역전은 **해결됨** (2026-09-02, 유니패스 대조). 25차는 남아 있다

## 조사 방법 (재현용)

라이브 DB 대사는 아래 순서로 한다. **anon PostgREST로 조회 가능한 테이블**은 `transactions` / `interim_settlements` / `closing_settlements` / `lc_fee_items` / `closing_cost_items` 등 대부분이고, `audit_logs`와 `pg_catalog`만 SQL 에디터가 필요하다.

1. `.env.local`의 `NEXT_PUBLIC_SUPABASE_ANON_KEY`로 PostgREST 조회 (조인은 `transactions?select=...,closing_settlements(...)`)
2. `node ./scratch.ts` 로 `lib/calculations/` 의 함수를 **실제 코드 그대로** 돌려 재계산한다
3. DB 확정금액 − 재계산값으로 차이를 낸다

전 차수를 한 번에 훑느라 다른 언어로 공식을 다시 구현했다면, **결과를 반드시 화면 값과 대조할 것.**
공식을 두 번 쓰면 두 벌이 어긋나고, 어긋난 쪽이 보고서로 나간다.

통관 사실관계(입항일·수입신고일·선사·컨테이너번호·Master B/L)는 **관세청 유니패스 오픈API**로 확인한다.
`lib/tracking/unipass.ts`(화물통관진행정보) / `lib/tracking/customsRate.ts`(관세환율)를 그대로 쓰면 되고,
인증키는 `.env.local`의 `UNIPASS_API_KEY_CARGO` / `UNIPASS_API_KEY_FXRATE` 다.
**출항일(ETD)은 제공하지 않고, 보관주기 3년이 지난 건은 조회되지 않는다.**

DDL·`audit_logs`·카탈로그 조회는 SQL 에디터에서 실행해야 한다. **Supabase SQL 에디터는 여러 문장을 실행하면 마지막 문장의 결과만 보여준다** — 여러 조회를 한 번에 받으려면 `UNION ALL` 로 단일 SELECT를 만들 것.

## 유의

- 담당자가 라이브 DB를 실시간으로 편집 중이다. 감사 결과는 스냅샷이므로 수치가 어긋나면 재조회한다 (예: 37차 항목 부가세가 152,470 → 156,180으로 변경된 사례)
- 확정금액을 바꾸는 SQL은 **실행 전 사용자에게 보여주고 승인받는다.** 금액이 큰 건(23차 5,780만원 등)은 담당자 컨펌까지 받는다
- 「확정금액 미갱신」 = 저장 후 LC수수료·결제비용·환율을 고쳤는데 확정금액이 재계산되지 않아 옛 값이 굳은 경우. 화면에서는 `OverrideMismatchNotice`가 경고와 되돌리기를 제공한다
- ⚠️ **2026-09-04 이전에 만든 대사 산출물(아티팩트·보고서·커밋 메시지)의 금액은 구규약 기준이다.**
  「항목 부가세 가산」이 들어간 분석은 전부 무효다. 숫자를 인용하기 전에 지금 화면 값과 대조할 것
- `fix_gross_customs_items.sql` 의 백업 테이블(`interim_cost_items_backup_20260904`)은 **비어 있다.**
  되돌리려면 `supabase/manual/restore_gross_customs_items.sql` 을 쓴다 (정정 전 스냅샷 62건)
